Visão de baixo nível do Knowledge Assistant. Cada bloco abaixo liga o conceito (o que está acontecendo), o código (onde isso vive no repo) e a decisão (por que foi feito assim e o que se abre mão). Complementa a visão visual.

1. Fronteiras de serviço

O enunciado pede Python para RAG e Go para REST. A decisão de desenho não é “dois apps que fazem a mesma coisa”: é um núcleo de retrieve+generate e duas fachadas (HTTP público e MCP).

GO · :8080

Superfície pública

Valida JSON, grava metadata em documents, faz proxy HTTP para o RAG. Não chunka, não embedda, não chama o LLM.

PYTHON · :8000

Dono do RAG

Chunk, MiniLM, pgvector, prompt grounded, Ollama. run_query() é a função única de consulta.

MCP · stdio

Só transporte

python -m rag.mcp importa run_query(). Não é um segundo pipeline. Schema do enunciado mapeia content → chunk.

Por que HTTP interno Go → Python, e não um monolito?

O desafio exige essa fronteira. Ganho: testes Go mockam um ragclient.Client sem MiniLM/Ollama; testes Python mockam vector store e LLM sem HTTP. Custo: um hop extra e orquestração de ingest em duas transações (veja §5).

Por que o mesmo Postgres para metadata e vetores?

O enunciado deixa “mesmo DB ou separado”. Um banco só = um Compose service, FK ON DELETE CASCADE, um .env. Abre mão de escalar o vector store isolado (Pinecone/Qdrant) — irrelevante no corpus de sample.

2. Schema — três tabelas, um contrato de dimensão

Texto não se busca com LIKE aqui. O documento vira N chunks; cada chunk vira um vetor de exatamente 384 floats. Esse número aparece em três lugares e os três têm que bater. 

documents  1 ──<  chunks  1 ── 1  embeddings
   id, title,           content,              embedding vector(384)
   source_uri           chunk_index           model_name
   ON DELETE CASCADE ──────────────►  ON DELETE CASCADE

Contrato dos 384

OndeO quê
VECTOR_DIMENSION.env / Settings Python
EMBEDDING_MODELall-MiniLM-L6-v2 (384-d)
vector(384)coluna SQL — tipo rígido

Trocar o modelo sem ALTER + re-embed quebra o ingest: o embedder recusa dimensão diferente, e o Postgres recusa o vector(n) errado.

Por que HNSW + vector_cosine_ops?
  • HNSW — grafo aproximado (ANN). Bom para latência em corpora pequenos/médios; o índice custa build, não é exact k-NN.
  • Cosseno — MiniLM é treinado para similaridade de sentença. Com normalize_embeddings=True, cosseno ≡ produto interno. Distância L2 seria outra geometria.
  • Operador <=> no pgvector = distância de cosseno (0 = idêntico). Score HTTP = 1 - distância para o cliente ver “maior = mais parecido”.
Por que UNIQUE (document_id, chunk_index) e UNIQUE (chunk_id)?

Re-ingest de um documento apaga os chunks antigos e reinsere. O único vetor por chunk evita duplicar a mesma janela no ANN. O índice em (document_id, chunk_index) serve o list/debug e o DELETE FROM chunks WHERE document_id = … do re-ingest.

3. Chunking — janelas com overlap

O LLM tem contexto finito e a busca é por trecho, não pelo documento inteiro. Fatia-se o texto em janelas de caracteres (CHUNK_SIZE=500) com overlap (CHUNK_OVERLAP=80). 

texto:  |---------------- 850 chars ----------------|
chunk 0: [------ 500 ------]
chunk 1:              [------ 500 ------]   ← recua 80 (overlap)
chunk 2:                           [-- 250 --]

Por que overlap? Uma frase na fronteira do chunk 0 ainda aparece no 1.
Sem overlap, a busca pode “cortar” o fato no meio.
Por que caracteres, não tokens nem parágrafos?

Corpus de sample é plain text curto. Janela de caracteres é determinística, fácil de testar (test_chunking.py usa "a" * 85) e não puxa um tokenizer. Tokens alinhavam melhor com o LLM; parágrafos falham em FAQs sem quebra. Para PDF longo, o próximo passo seria splitter semântico — fora do escopo.

Invariantes que o teste trava
  • Overlap < size — senão o start não avança (loop infinito).
  • Texto só whitespace → lista vazia → ingest vira 400, não uma linha fantasma no pgvector.
  • Defaults 500/80: ~80–120 tokens, cabe várias frases; overlap ~1 sentença.

4. Embeddings — o texto vira geometria

Um embedding é um ponto em ℝ384. Trechos sobre o mesmo assunto ficam próximos; a pergunta é embeddada com o mesmo modelo para cair no mesmo espaço.

Por que MiniLM local, não OpenAI embeddings?

Zero custo de API, funciona offline no Compose, dimensão pequena (384 vs 1536). Trade-off: primeira subida baixa o modelo Hugging Face (minutos); ingest em CPU é mais lento. A qualidade é suficiente para FAQ/docs curtos do sample.

Por que normalize_embeddings=True + check de dim?

Sem normalizar, cosseno e L2 divergem e o índice vector_cosine_ops deixa de ser a métrica “natural”. O check de dimensão falha cedo (ValueError no Python) em vez de um erro opaco do Postgres no INSERT.

Por que @lru_cache no load do modelo?

Carregar MiniLM/torch é caro. HTTP FastAPI carrega uma vez no lifespan; MCP atrasa esse load até a primeira tool call (handshake JSON-RPC precisa ser rápido — senão o Claude Desktop acha que o server travou). Ver §9.

5. Ingest — duas transações, um rollback cuidadoso

Go insere a linha de metadata antes de chamar o Python. O Python faz upsert do título, apaga chunks antigos e grava os novos numa transação. Isso não é acid em dois serviços — e o código documenta exatamente o que acontece no timeout.

01

Go valida e INSERT. Gera UUID, grava title, source_uri, content_type. O RAG não conhece source_uri.

02

Go POST /ingest no RAG com o mesmo document_id + texto.

03

Python chunk + embed e, numa transação: upsert documents, DELETE FROM chunks (cascade embeddings), INSERT chunks+vetores.

04

Erro HTTP do RAG → Go apaga a linha. Timeout → não apaga: a transação Python ainda pode commitar e recriar o documento.

Por que o Go insere primeiro, se o Python já faz upsert?

Para preservar source_uri (origem do arquivo / upload). O upsert Python só toca title + updated_at — se o Go não tivesse inserido, o campo ficaria NULL. Re-ingest pelo mesmo UUID substitui chunks (DELETE + INSERT) sem duplicar o documento na listagem.

6. Retrieval — a pergunta no mesmo espaço

Query ≠ keyword search. Embedda a pergunta, pede ao pgvector os top_k vizinhos (default 5), devolve texto + score. Zero hits → o LLM não é chamado.

Por que score = 1 - (a <=> b)?

pgvector ordena por distância (menor = mais perto). A API pública expõe similaridade ∈ (~0, 1]: 1.0 = vetores iguais. O cliente e o MCP mostram “score”, não “distância”.

Por que 404 em corpus vazio, não “não sei” do LLM?

O enunciado pede resposta grounded. Se não há chunks, não há contexto — chamar o modelo seria alucinar com conhecimento pré-treinado. NoRelevantChunksError vira HTTP 404 no_relevant_chunks. O teste unitário afirma que o spy do LLM called is False.

7. Prompt grounded — o LLM só vê os chunks

Retrieval escolhe o texto; o prompt escolhe as regras. Sem a instrução “não use conhecimento externo”, um modelo local ainda completa com o que memorizou no treino.

Por que numerar os chunks no contexto?

Dá âncora ao modelo (“segundo [2]…”) e deixa o log do prompt auditável. As fontes na resposta HTTP/MCP não vêm do modelo — vêm dos hits do pgvector. O LLM não escolhe as sources; o código as anexa.

Ollama: local vs cloud no mesmo client

OllamaClient POSTa /api/chat com stream: false. Bearer só vai para host ollama.com — o daemon local rejeita token de cloud. Timeout vira llm_timeout (504); rede cai vira llm_unavailable (503).

8. API Go — fachada idiomática

cmd/api/main.go só liga pool, client e HTTP server. Handlers em internal/httpapi devolvem error; um wrap traduz para JSON {"error","message"}.

Interface do RAG — fronteira de teste

handlers_test.go usa stubRAG. Os testes cobrem validação, 201, proxy do document_id, 404 upstream e rollback — sem Python no PATH.

Detalhes que não são acidentes
  • WriteTimeout = RAGClientTimeout + 15s — query espera o LLM; o default de 30s mataria a request.
  • captureWriter — ServeMux nativo devolve texto “404 page not found”; o middleware reescreve para JSON.
  • mux.ServeHTTP no request original — PathValue("id") só funciona assim (comentário no código).
  • DELETE → 204 No Content sem body; CASCADE no SQL apaga chunks e embeddings.
  • Go não busca vetor. Query é validação + proxy.

9. MCP — transporte, não segundo RAG

MCP é JSON-RPC em stdout. Qualquer print() ou barra de progresso do Hugging Face no stdout quebra o cliente. Logs vão para stderr; o modelo MiniLM só carrega na primeira chamada da tool.

Schema do enunciado vs HTTP

Por que MCP não entra no Compose?

Claude Desktop (e clientes MCP) spawnam o processo e falam stdio. Um container no Compose não tem quem fale nesse pipe. Postgres e Ollama precisam estar no ar; o corpus já ingerido. Env do MCP tem que apontar para o mesmo DB/Ollama que o serviço RAG — senão a tool consulta um banco vazio.

10. Erros — códigos estáveis, mensagem humana

Dois envelopes: FastAPI usa detail: {error, message}; Go unwraps isso e devolve o mesmo par na raiz. Clientes (UI, curl, testes) só precisam de um contrato.

codeHTTPQuandoDecisão
invalid_request 400 title/text/question vazios; top_k fora 1–50 Falhar na borda, não no LLM
no_relevant_chunks 404 corpus vazio ou busca sem hits Não alucinar
not_found 404 DELETE de UUID inexistente; rota inexistente JSON, não texto do ServeMux
llm_unavailable 503 Ollama inacessível Retry faz sentido
llm_timeout 504 chat excedeu OLLAMA_TIMEOUT_SECONDS Separado de “rede caiu”
llm_error 502 401, body vazio, JSON inválido Upstream falhou de verdade
rag_unavailable 502 Go não alcança o Python Fronteira de serviço visível
Por que RAGError.code em vez de except Exception?

O mapa _ERROR_STATUS em app.py traduz domínio → HTTP sem um handler gigante. Testes afirmam o error string, não só o status. Bare except está fora das regras do repo.

11. Testes — mockar a fronteira certa

O enunciado pede TDD thinking, não 100% de coverage. Mocka-se o que é lento, caro ou externo; deixa-se real o que é o contrato (SQL, HTTP shape).

PYTHON UNIT

Fake store + spy LLM

test_retrieval.py: embedding e top_k chegam ao store; lista vazia não chama chat(). test_generate.py / test_prompt.py travam o contrato do prompt.

GO UNIT

stubRepo + stubRAG

handlers_test.go: health, ingest 201, list, delete 204, validação, mapeamento de erro upstream. Zero MiniLM.

INTEGRAÇÃO

Postgres real, LLM stub

test_integration.py: embedder determinístico 384-d (sem baixar o modelo). Ingest + query contra o schema de verdade. Skip se o DB não estiver no ar.

Por que o embedder da integração é um vetor [1, 0, 0, …]?

O teste quer provar “ingest grava, query lê, o prompt contém o chunk”. Não quer provar qualidade de MiniLM. Vetor constante faz pergunta e documento coincidirem no ANN sem baixar 80MB de pesos. O stub do LLM ainda exige que a palavra “MiniLM” esteja no contexto — senão o grounding quebrou.

12. Compose e o que ficou de fora

Um comando sobe db, ollama, rag, api e web. Schema só roda no primeiro start do volume.

Por que docker compose down -v para reaplicar o schema?

docker-entrypoint-initdb.d só executa em datadir vazio. Mudou vector(384)? Precisa volume novo (ou ALTER + re-embed). É o trade-off de não ter um runner de migrations no take-home.

Limitações conscientes
  • Seed só *.txt — sem pipeline PDF.
  • make ingest é idempotente: se já existe documento, não reseeda.
  • REST sem auth (escopo do desafio).
  • MCP no host, não no Compose.
  • ANN sem filtro por metadata além do JOIN — corpus único.
